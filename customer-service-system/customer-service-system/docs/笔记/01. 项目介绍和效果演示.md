## 一、项目介绍

**一句话定位**：这是一门「把大模型接进真实业务数据，并让写操作可控」的实战课，以后端与 Agent 链路为主线，前端随课提供完整代码。成品是一个电商数据分析 Agent：用自然语言提问，系统先在数据库或向量库里找证据，再依据证据给出回答；低风险诊断报告自动保存，涉及预警或商品待复核的动作则必须人工确认。

**实现方式**：LangGraph 工作流 + 角色分工——规则代码负责查询路由、角色交接与动作决策，大模型负责 SQL 生成与回答总结。

**成品形态**：FastAPI + Vue 3 前后端，自带示例数据（20 商品 / 49 订单 / 46 评价，含 4 张带图评价）。本节与后续各集的演示都基于这套数据。

**和「只调用大模型 API 的聊天机器人」的区别**：只调用模型、不接业务查询工具时，回答主要依赖模型已有知识与对话上下文。这套系统增加了三件事——**去哪里查**、**如何处理查回来的证据**、**要不要写数据**；运行过程可回看。

四条能力主线：

| 部分 | 解决的问题 |
| --- | --- |
| 查询能力 | 结构化查询、语义检索、两者如何选择 |
| 编排能力 | 多步骤流程与多智能体如何组织和调度 |
| 行动与确认 | 写操作的判断、人工确认、失败恢复 |
| 工程能力 | 工具化（MCP）、运行历史、多模态、前端 |

三条底线：

1. **业务查询只读**：不修改订单、库存、价格、上下架，允许的写入只有诊断报告、站内预警和商品待复核标记；
2. **高风险动作必须人工确认**：动作包含预警或待复核时，整组业务动作挂起等确认，取消即跳过；
3. **证据要相关、归属要明确**：相关性不足不规划业务动作，预警与待复核按商品分别判断；查询有行数上限与超时，统计类问题查不出来时明确说明，不拿评价片段代替统计。

**前置要求**：Python 基础语法（能看懂函数与类）、了解 HTTP 与数据库概念。不要求提前掌握 LangGraph、向量检索、Vue。

## 六、效果演示：三个示例

每个示例给出提问原文与观察重点，分别覆盖系统的三条主要路径。演示基于课程示例数据；SQL 由模型生成，语义召回受向量模型与索引内容影响，具体返回以当次运行结果为准。问题措辞会影响查询方式：识别到商品名、订单号或数量与统计口径时走结构化查询，否则默认语义检索（规则在「查询路由」一集展开）。

### 示例 1：用自然语言查询数据库（结构化查询）

```
洗衣液 2L 有哪些评价？
```

- 过程区依次显示：调度 → 查询分析 Agent（路由判断 → 结构化查询）→ 报告决策 Agent；这一步下面是本次生成的 SQL 原文，可以拿去数据库执行核对；
- 系统先判断「该走 SQL」，再生成 SQL 去查，而不是把问题直接丢给大模型；
- 回答涉及的评价可在「评价数据」页面逐条核对；本例只保存低风险报告，不进入确认流程。

**延伸阅读**：NL2SQL、SQL 安全校验（查询能力）。

### 示例 2：换一种说法也能搜到（语义检索）

```
跑鞋脱胶
```

- 该商品那条带图 1 星评价原文写的是「鞋底开胶了」，与提问用词不同，仍被召回；
- 图片描述入库后，这条评价的检索文本带 `【晒图内容】`——视觉模型生成的描述与正文一起参与检索；描述失败时索引保留纯文字评价，结果里就没有这个标记；
- 「距离」衡量相似程度（余弦距离 = 1 − 余弦相似度），越小越相似；「语义检索」页面可以直接看命中片段与距离。

**延伸阅读**：向量检索与索引、图片描述接入检索。

### 示例 3：高风险操作必须人工确认

```
轻云运动跑鞋的差评有点多，看看并处理。
```

- 证据触发预警或待复核动作时，系统暂停整组业务动作，弹出「需要人工确认」卡片，卡片里列出待执行动作与判断依据；确认后执行整组动作，取消则跳过，两种结果都记入运行历史；
- 低分评价按商品分别累计，达到阈值才规划预警与待复核（阈值与计数口径在「动作决策」一集展开）；
- 写入结果在「诊断报告」页面查看：诊断报告与预警通知两个页签，未读可逐条或一次性标记已读。

**安全边界**：系统能做到的止步于「标记 + 通知」，真正的处置仍由人做——Agent 在商品表上唯一能改的是一个两值字段，价格、库存、上下架、订单状态全部只读。

**延伸阅读**：动作决策、人工确认与恢复（行动与确认）。

## 七、多智能体协作：三个角色

一次问答不是一个大模型从头干到尾：三个角色落在同一张 LangGraph 上，各自负责一组节点，角色之间由调度节点按固定规则交接——所以过程可回看、每一步可独立替换。

| 角色 | 负责的步骤 | 可以做什么 | 不做什么 |
| --- | --- | --- | --- |
| 调度 | 流程启动、Agent 之间的交接 | 按预定义流程交接任务、更新当前角色 | 不查数据、不规划业务动作 |
| 查询分析 Agent | 路由判断 → SQL / 语义查询 → 深挖 → 证据准备 | 检索数据、整理证据 | 不决定写什么数据 |
| 报告决策 Agent | 动作决策 → 人工确认 → 执行 | 按规则规划动作、必要时请求确认、执行允许的写操作 | 不负责找证据 |

在界面上：每一步的标签显示当前是哪个角色在工作，两个角色之间会经过一次「调度交接」，示例 3 能完整看到这一次交接。

## 九、总结

这个项目最有价值的几项：

1. **自然语言转 SQL 的完整链路**：从生成、SQLGlot 结构校验、表白名单与防绕过、行数封顶与执行超时，到报错回喂模型自纠一次、统计查询失败时明确说「给不出统计结论」；
2. **写操作的安全边界与人工确认**：业务查询全只读；Agent 在商品表上唯一能改的是一个两值字段；动作里只要包含预警或待复核，整组业务动作就挂起等确认、取消即跳过，另有单进程并发保护和总结失败后的待确认恢复；
3. **查询路由与语义检索的证据判断**：先判断问题该去哪里查（点名商品、订单号、数量与统计口径走结构化查询；模糊主题走语义检索），再判断召回的片段配不配当证据（距离阈值、纯语义证据不参与高风险动作判断、统计问题不拿评价片段冒充）；
4. **多模态真正接进检索**：晒图先由视觉模型转成中文描述，与评价正文一起向量化，图片里的内容因此也能被检索到——用只出现在图片描述里的词（如「鞋底断裂 中底分离」）能命中那条评价；
5. **多 Agent 分工与过程可见**：调度、查询分析、报告决策三个角色各有职责边界——找证据的不写数据，写数据的不找证据；角色之间由调度交接，过程通过 SSE 事件回放到前端的流程区；
6. **把能力做成可复用、可回看的工程件**：MCP 把系统能力标准化成工具供其他 Agent 调用，观测表与看板把每次运行变成可回看的记录；

一句话：**先想清楚不许它做什么，再想它能做什么**。
