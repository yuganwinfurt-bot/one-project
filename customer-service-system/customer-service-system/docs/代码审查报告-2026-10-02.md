## 1. [P1] SQL 白名单没有覆盖全部表引用

位置：[nl2sql_service.py:175](D:/Code/Course/ecom-analysis-agent/backend/app/services/nl2sql_service.py:175)

表名通过正则查找 `FROM/JOIN` 后的标识符，逗号表检查又在第一个 JOIN 处截断。这两种有效写法均能通过 `validate_sql`：

```sql
SELECT (SELECT password FROM/**/users LIMIT 1) AS leaked
FROM products LIMIT 1;

SELECT u.password
FROM products p JOIN reviews r ON r.product_id=p.id, users u LIMIT 1;
```

在隔离 SQLite 中使用虚构 users 数据，两条语句均读取到 `FAKE_HASH`。这验证了校验器接受越界查询及查询结构的有效性；未在现有 MySQL 上读取用户数据。若模型被引导生成此类 SQL，当前共享数据库账号有 users 表访问权时，普通登录用户通过 NL2SQL 调试接口即可取得白名单外结果。

建议：使用支持 MySQL 的 SQL 解析器检查所有查询层级中的表引用和语句类型，或限制为可以严格验证的 SQL 子集；查询账号再使用数据库权限限定可读表。回归测试应覆盖注释、混合 JOIN/逗号表、嵌套查询和限定名。

## 2. [P1] 同一任务的并发确认会重复执行动作

位置：[chat_service.py:562](D:/Code/Course/ecom-analysis-agent/backend/app/services/chat_service.py:562)

`resume_actions` 先读取快照判断待确认，再调用 `graph.stream(Command(resume=...))`。整个过程没有按 thread_id 加锁，也没有原子消费确认或动作幂等标识。两次请求可以同时看到 `confirm_gate` 待恢复，然后各自执行写报告、写预警。

独立复现使用实际图、实际中断恢复和两个线程，在替代执行节点设置同步屏障；两个确认请求均成功，执行器被调用 **2 次**。前端 confirming 只限制一个页面的点击，不能防止多标签页或直接并发请求。

建议：对任务确认进行原子状态迁移，并为业务动作建立唯一幂等键。单进程锁能防止当前演示部署的竞争，多进程部署需要共享状态或数据库约束。

## 3. [P1] 聚合查询的多行结果被误去重，只保留第一行

位置：[nodes.py:67](D:/Code/Course/ecom-analysis-agent/backend/app/agent/nodes.py:67)

`_evidence_fingerprint` 在没有 review_id/id/content/text 时，所有行都会得到相同的 `text:` 指纹。NL2SQL 的分组统计通常返回商品名、金额、数量等列，不带上述字段，因此多商品对比、分组销量等结果会被折叠成一行，再交给模型总结。

复现输入三行 `product_name/sales` 分别为 shoe/100、shirt/200、cup/300，`node_prepare_evidence` 输出 **1 行**，只保留 shoe/100。

建议：结构化结果缺少实体键时保留各行，或对完整规范化行计算指纹。不同实体类型的 ID 也应采用不同命名空间，避免订单 ID 和评价 ID 偶然相同造成误合并。

## 4. [P2] LIMIT 校验读取内层或注释中的数字，外层返回没有硬上限

位置：[nl2sql_service.py:231](D:/Code/Course/ecom-analysis-agent/backend/app/services/nl2sql_service.py:231)

`_extract_limit/_cap_limit` 只匹配第一个 LIMIT，无法区分注释和查询层级。以下两条语句均通过校验，且执行时不会正确限定外层：

```sql
SELECT * FROM reviews -- LIMIT 1

SELECT * FROM reviews
WHERE product_id IN (SELECT id FROM products LIMIT 1)
LIMIT 100000
```

使用隔离数据及实际 `execute_select`，仅忽略 MySQL 专属的超时 SET，两条查询均返回 **250 行**，超过 MAX_ROW_LIMIT=200。`mappings().all()` 仍会加载完整结果；查询超时不能替代返回行数限制。

建议：基于解析后的最外层查询限制行数，并在取数层限制读取量；对注释、子查询和各 LIMIT 形式增加执行级测试。

## 5. [P2] 业务错误被 Axios 当作成功，确认失败后仍清除待办

位置：[request.js:27](D:/Code/Course/ecom-analysis-agent/frontend/src/utils/request.js:27)

后端 BusinessException 使用 HTTP 200 加非 200 的业务 code 返回。Axios 成功拦截器对非 401 业务错误仅弹提示，随后仍 `return data`。Chat.vue 的确认、取消和反馈逻辑直接认为 await 成功，不再判断业务 code。

实际 Axios 拦截器复现：返回 `{code:500,message:'task expired',data:null}`，Promise 仍 **resolved**。因此确认失败时页面会提示“已执行 0 个动作”并清除 pendingAction，catch 中的失败处理不会运行；反馈失败也可能显示已点赞。

建议：所有非 200 业务 code 都 reject；401 额外处理登出。确认失败必须保留待确认任务及重试入口。

## 6. [P2] 去重时丢弃同一评价新增的图片描述

位置：[nodes.py:209](D:/Code/Course/ecom-analysis-agent/backend/app/agent/nodes.py:209)

lesson-11 把图片描述只写入 Chroma 文档，结构化评价仍只有原文。合并时只要 review_id 已存在，就跳过整个语义证据，没有把图片内容合入已有评价。

复现：结构化评价 id=7、content='bad'；语义侧 review:7 文本包含图片描述 'sole detached'；最终证据只有 'bad'。明确商品查询进入结构化分支再深挖时，图片识别结果因此无法到达总结模型。

建议：识别为同一评价时合并图片描述和来源信息，同时保留一条评价用于计数；避免通过重复加入证据来抬高差评数量。

## 7. [P2] JWT 将本地无时区时间当作 UTC，过期时间偏移

位置：[jwt.py:10](D:/Code/Course/ecom-analysis-agent/backend/app/utils/jwt.py:10)

`datetime.now()` 生成无时区的本地时间，而 PyJWT 转换 exp 时按 UTC 处理。当前 Asia/Shanghai 环境中，配置 24 小时实际生成约 **32 小时**有效期；在负 UTC 偏移环境中会缩短有效期。

复现仅计算生成 token 的 exp 与 `time.time()` 的差值，未输出 token 或密钥。

建议：JWT exp 使用 `datetime.now(timezone.utc)`，或使用 epoch 时间戳计算；数据库展示时间可以继续采用现有本地时间约定。

## 8. [P2] 人工确认通知依赖回答生成成功，模型失败后任务失去操作入口

位置：[chat_service.py:414](D:/Code/Course/ecom-analysis-agent/backend/app/services/chat_service.py:414)

图已经在 confirm_gate 中断，但 stream_chat 先完整调用 `_stream_answer`，再发送 action_pending。如果总结模型超时或失败，异常分支把运行标记为 error，前端没有收到 thread_id 和待执行动作；历史页面也没有恢复确认入口。

独立复现：高风险图暂停后让回答模型抛 BusinessException，收到 error，但 **action_pending 事件数为 0**，图仍停在 `('confirm_gate',)`。任务实际待确认，页面却无法继续。

建议：保存并及时暴露待确认状态，使其独立于回答流成功；至少在回答失败时仍返回任务 ID 和待确认信息，并提供历史恢复入口。

## 9. [P2] 已有诊断报告或预警后，重跑种子脚本被外键阻止

位置：[seed_ecommerce.py:267](D:/Code/Course/ecom-analysis-agent/backend/data/seed/seed_ecommerce.py:267)

清理脚本只删除 reviews、orders、products，但 diagnosis_reports 和 alert_notifications 的 product_id 仍引用 products。完成一次带商品报告或预警的演示后，再按 README 重跑 seed，删除 products 会触发外键错误。

在启用外键的内存 SQLite 中，插入商品及关联诊断报告后调用 `_clear_ecommerce_tables`，复现 IntegrityError。未清理现有教学数据库。

建议：明确教学数据重置范围，对关联产物先清理或解除引用，并将整个重置过程设计为事务；不要通过关闭外键检查留下悬空引用。

## 10. [P2] 反馈接口没有验证运行归属，其他用户可写入反馈

位置：[observability/service.py:163](D:/Code/Course/ecom-analysis-agent/backend/app/observability/service.py:163)

列表与详情接口限制普通用户查看自己的运行，但 submit_feedback 只校验 run 是否存在，没有验证归属。普通用户可以直接对其他用户的顺序 run_id 提交点赞或点踩。详情又显示该运行最新的一条反馈，因此可污染他人的反馈结果。

隔离数据库复现：user_id=1 的运行，接受 user_id=2 的反馈。

建议：反馈提交沿用运行详情的归属权限规则；如管理员可以跨用户反馈，API 应明确传递并校验该权限。
